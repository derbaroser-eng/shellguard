The bug

Every automation system eventually does this:

full = f"cd {dir} && run --model {model} {prompt}"
subprocess.run(full, shell=True)

A prompt containing ( makes bash abort with syntax error near unexpected token. A prompt containing backticks or dollar-parens executes attacker-chosen commands. Both failures were observed in production.

The rule

Never build a shell string from untrusted text. Build an argv list. execve semantics keep each token a token — no parser, no metacharacters, no surprises.

import shellguard as sg

sg.run(["echo", "(17*23)"])          # -> "(17*23)\n"
sg.run(["echo", "`echo INJECTED`"])  # -> literal text, not a command
sg.run(["echo", "$(echo INJECTED)"]) # -> literal text
sg.run(["false"])                    # -> Result(returncode=1, ok=False, ...)

What you get

argv, not strings

build() returns a list; run() execs it directly. shell=True and bare-string commands are refused by design.
