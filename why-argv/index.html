A parenthesis broke our command. Here's the rule that fixed it.

Field note · 22 November 2026 · 7 min read

I still remember the error line. Not the whole incident — just this:

bash: -c: line 1: syntax error near unexpected token `('

Someone had typed (17*23) into a prompt field, and our automation had pasted that text straight into a shell string. The command died before it ran. Nobody was attacking us. A perfectly ordinary human input was enough.

The crash was not the scary part. The near miss was. If that same person had typed backticks or $(...), the shell would have run whatever was inside. Same code path, same bug, much worse afternoon.

I have seen that shape since in CI helpers, deploy scripts and more than one agent framework. It always looks like this:

full = f"cd {cd} && {oc} run --model {model} {prompt}"
subprocess.run(full, shell=True)

It reads fine. It looks like a command. And that is exactly the problem: it is a command, assembled out of pieces that somebody else controls.

The habit that actually fixes it

Stop building shell strings. Build argument lists.

When you hand the operating system an argv list, there is no parser in the middle. Every element is one token, whether it holds a parenthesis, backticks, a semicolon, a newline, or the word rm. Nothing gets reinterpreted. That is execve semantics, and it has been the right answer for decades — we just keep forgetting it when a string is convenient.

import shellguard as sg

sg.run(["echo", "(17*23)"])          # prints (17*23)
sg.run(["echo", "`echo INJECTED`"])  # prints those characters, literally
sg.run(["echo", "$(touch pwned)"])   # no file is created

Notice what did not happen: no escaping, no denylist, no regex that tries to guess which characters are dangerous. Escaping is where people lose. Every denylist has a character nobody thought of. An argument list does not care.

The case that keeps catching people out

Shell metacharacters are the famous bug. The quieter one is argument injection, CWE-88. Suppose a user controls a value that lands as a separate argv token:

subprocess.run(["curl", url, output_flag])   # output_flag = "-o /etc/passwd"

No shell is involved, so the usual "never use shell=True" advice says this is fine. It is not. The program receiving those arguments treats -o as an option. You handed the user control of the program's flags.

There is a second version of this that bit us on Git Bash and MSYS. A plain * in an unquoted token gets expanded by the shell layer before the program sees it. The token was data; the runtime turned it into a glob. Our audit engine flags both cases — a provable leading - on an untrusted token, and wildcard characters that MSYS would expand.

The rule of thumb I use now: if untrusted text can become a token, either put it after an explicit -- where the tool supports it, or validate it against a strict shape. "It is in an argv list" solves shell injection. It does not solve option injection.

How we stopped arguing about it

Opinions do not survive a deadline. Tests do. The library has 126 of them, and the suite is the product more than the code is. It encodes the ways a shell-string builder actually fails: parentheses, backticks, $( ), semicolons, pipes, &&, newlines, quotes, globs, tilde, environment expansion, redirection, unicode, binary bytes, timeouts, working directories, and stdout/stderr separation. Plus cases for forged license keys, CLI exit codes, and the audit scanner itself.

There is also a self-audit: a GitHub Action scans the library's own source for shell=True, os.system, os.popen, asyncio.create_subprocess_shell, and string-built argv, including aliased imports. It runs on every push and fails the build on findings. I like that arrangement — the tool is held to the same standard it sells.

What it will not do for you

Worth being blunt about the edges. The taint analysis is intra-file and intra-function. It will not follow a value through a call into another module, and it does not attempt to understand dynamically built command prefixes. If your danger lives in a different file, the scanner will not connect the dots. Unsupported languages and files it cannot parse are reported as skipped, with the reason, instead of being quietly counted as clean.

And no tool in this space can honestly promise compliance. What you can get is a dated, signed record of what was examined, what was found, and what was out of scope. That is a much more useful artifact than a green checkmark with no memory.

Try it

Zero dependencies, Python 3.8+, stdlib only. No network calls, no telemetry.

pip install https://github.com/derbaroser-eng/shellguard-lib/releases/download/v1.4.0/shellguard-1.4.0-py3-none-any.whl
